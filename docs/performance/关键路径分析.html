关键路径The critical path of a device execution

一次 kernel 运行的时间，究竟消耗于有效计算，还是消耗于等待？ 关键路径提取出决定总时长的那条任务链，并对其逐段归因。本文档系统阐述这一概念， 并剖析 critical_path.py 的实现原理及其全部产物。

纯后处理 · 不占设备 复杂度 O(N log N) 输入 --enable-l2-swimlane 两条路径 static / observed
00 导论 · Introduction

什么是关键路径，为什么要找它

任何由相互依赖的任务组成的系统里，有些任务必须等另一些先完成。把「谁依赖谁」画成一张 有向无环图（DAG），其中时长加权最长的那条依赖链就是 关键路径——它的长度决定了整件事最快能多久完成，因为链上各步只能依次发生、无法并行压缩。

由此得到关键路径最重要的两条性质：链上的任务没有余量（slack）——任一变慢，makespan 立刻变长； 链外的任务有余量——像 D，推迟或适度变慢都不影响总时长。

为什么性能分析离不开它

因为关键路径就是时间真正花掉的地方，也就是性能提升点之所在： 只有压缩关键路径上的任务，makespan 才会缩短；优化链外任务只是消耗它们本就有的余量，端到端毫无变化。 换言之，关键路径把「该优化谁」从成百上千个任务里直接圈了出来——这就是我们要找它的全部理由。

落到 Ascend kernel 执行上：一次运行由成百上千个任务组成（Host 下发、AICPU 调度、AICore 执行），端到端只给一个「耗时 0.7 ms」，既不区分计算与等待、也不指出该优化谁。 L2 swimlane 让每个任务的 start / end 可观测，而 critical_path.py 据此把那条决定性的关键链自动重建出来。

记号

makespan ＝ max(end) − min(start)，即设备墙钟总时长；全文百分比均以其为分母。

谱系：从项目调度到 DAG 最长路径

为什么「最长路径」可以高效求解

一般图上的最长（简单）路径是 NP-hard（可由 Hamilton 路径归约）；但任务图是 DAG——无环使拓扑序存在，沿拓扑序一遍动态规划即得精确最长路径，复杂度 O(V+E)。 这既是经典 CPM 可解的原因，也是本工具能廉价重建关键路径的根本。

形式化：定义与递推

记任务图 G = (V, E) 为 DAG，d(v) ≥ 0 为任务时长， pred(v) / succ(v) 为前驱 / 后继集。前向遍历给出最早时刻， 后向遍历给出最晚时刻，二者之差即时差（slack）。

算法（伪代码）

DAG 最长路径 = 拓扑排序 + 一遍动态规划，均为 O(V+E)，回溯即得关键路径。 下面两段分别对应 critical_path.py 的 topo_order 与 static_cpm。

01 定义与示例 · Definition

总时长由最长的依赖链决定，而非最繁忙的计算核

把导论里的概念落到真实 kernel 图上。下图是一次 decode 前向的依赖 DAG——同样地， 决定总时长的是最长依赖链，而不是最繁忙的那个核：某个核可能一直在算， 但若它算的都是有余量的任务，加速它也不会让 makespan 变短。

软件构建、任务调度、流水线编排本质上都是同一个问题：识别并压缩这条主线。

02 分析动机 · Motivation

关键路径明确指示优化投入的方向

性能优化中的常见失误，是优化了并不处于关键路径上的部分——投入大量精力，端到端时长却毫无改变。 关键路径给出两条基本原则：

  • 唯有压缩关键路径上的时间，makespan 方能缩短。路径之外的任务存在余量， 对其优化只是消耗余量，并不改变总时长。
  • 沿关键路径，makespan 可被精确切分为两类时间—— compute（有效计算）与 stall（等待）。二者的比例直接表明该 workload 属于算力受限还是调度 / 依赖受限，二者的应对方式截然不同。
要点

该工具的核心价值可概括为：将一次运行归结为「compute 与 stall」「observed 与 static」 两组对比，据此判断应优化算子实现，还是应调整依赖 / 调度，使优化决策有据可依。

为何需要两类产物

l2_swimlane_records.json 仅包含时序——每个 (task, core-block) 的执行时间片，而不含依赖（设备热路径有意不记录 fanout）。 依赖来自独立的 deps.json（由 dep_gen 离线重放生产者→消费者边生成）。 name_map.json 负责将 callable_id 映射为可读的 kernel 名称。 工具将三者按 task_id 连接（deps 中为字符串、swimlane 中为整数，统一归一化为字符串以避免静默漏连）， 由此同时获得任务的执行时刻与任务间的依赖关系。

04 工具剖析 · Anatomy

建图之后，两条路径刻画不同的约束

build_graph 为每个 rank 构建一张 RankGraph，完成三项工作：

  • 逐任务时序。同一 task 可能被拆分到多个 core-block 上并行执行，取所有分片的 min(start) 与 max(end)，得到该任务的 start / end / dur。
  • 数据依赖前驱 hb_pred（happens-before）。遍历 deps.json 的每条 p→s 边，仅当 end[p] ≤ start[s] + tol 且 start[p] < start[s]（严格更早开始）时保留；严格开始条件保证保留图无环（见下方引理）。
  • 同核资源前驱 core_prev。任务落在某核上时，该核的空闲时刻 决定其能否更早开始。按核对时间片排序，以运行最大 end（running-max，可正确处理流水 / 重叠分片） 确定其落核前该核被占用的最晚结束时刻。

基于 hb_pred（数据）与 core_prev（资源）两类前驱，工具计算出两条用途不同的路径。 二者的区别，正是理解 static 与 observed 的关键所在。

A · static_cpm

静态 CPM · 依赖受限的延迟下界

仅考虑数据依赖，并假设计算核无限。在 happens-before DAG 上执行经典的 最长时长加权路径算法（Critical Path Method）：拓扑排序后以 DP 求各任务的最早完成时间，回溯得最长链。

它给出任何调度都无法低于的延迟下界——因为链上的数据依赖无法回避。 CPM 越接近 makespan，表明瓶颈越在于依赖链本身；进一步加速只能通过重构依赖图（拆分、消除串行）实现。

finish[v] = max(finish[p] for p in hb_pred[v]) + dur[v]

理论：无资源约束的先验关键路径 = DAG 最长路径，多项式 O(V+E) 可解。

B · observed_path

观测路径 · 实际执行的归因链

从最后完成的任务反向回溯。每一步在当前任务的候选前驱 （数据依赖 hb_pred 与同核资源 core_prev）中，选取结束最晚、 对其开始约束最紧者作为主导前驱，并记录相应的停顿类别。

该链依据实际执行过程得出，因此可能同时包含数据等待与资源串行化 （不同于 static CPM 仅沿数据依赖边；具体包含哪些取决于 workload），且其各段能对整个 makespan 精确切分覆盖。

cand = hb_pred ∪ core_prev → 取 end 最大者 → {data-wait | core-wait | front-gap}

理论：有资源约束调度的后验关键路径；主动求解即 RCPSP（强 NP-hard），此处不求解，而是从已实现调度回溯重建。

理论保证

引理 · 保留图无环
保留边 p→s 要求 start(p) < start(s)。
证. 若存在环 v₁→…→v_k→v₁，则 start(v₁) < … < start(v₁)，矛盾 ⇒ 保留图无环，拓扑序存在，DP 与反向回溯均良定义。
定理 · 静态 CPM 精确且多项式
拓扑序上一遍 EF-DP 即得精确最长加权路径，O(V+E)。
要点. 拓扑序保证求 EF(v) 时其所有前驱已算完；DAG 的无环性把一般图 NP-hard 的最长路径降为线性可解。
定理 · 精确铺分 tiling
沿 observed 路径，Σ(gapᵢ + effᵢ) = t₁ − t₀ = makespan。
证. 每步 gapᵢ + effᵢ 恰把 frontier 从前值推进到 max(frontier, eᵢ)；望远镜求和得 frontier 末 − frontier 初 = t₁ − t₀。故 compute + stall 恒等于 makespan（tiling check 必为 exact）。
复杂度
总体 ≈ O(N log N)，纯后处理、不占设备。
主导项为每核时间片排序 O(R log R)；建图、拓扑排序、两次 DP / 回溯均为 O(V+E)。R 为分片数，可略大于任务数 N。

三类停顿的定义

observed 路径上的每一段停顿均被归类，此即报告中 stall kind 的来源：

  • data-wait——受阻于上游生产者，即等待数据。
  • core-wait——受阻于计算核被占用，即资源串行化（数据已就绪，但无空闲核可用）。
  • front-gap——回溯至无任何前驱的链首，即首个任务之前的启动 / 派发延迟。

同一数据下两条路径的对比

observed 路径对 makespan 的精确切分

沿 observed 路径执行一次前沿扫描（frontier sweep）：维护一个已覆盖到的时间点 frontier。对路径上每个任务 [s, e]， s 之前的空档计为 stall， 该任务未与前段重叠的净时长计为 compute，随后将 frontier 前推至 e。 由于该链连续，各段的 compute + stall 之和恰好等于 makespan—— 报告中的 tiling check 即用于校验此等式（结果应为 exact）。

05 产物解读 · The report

critical_path_report.md 的结构与解读

工具在被分析目录下生成 critical_path_report.md，每个 rank 一节，包含三个部分： 概览、按 kernel family 汇总与逐任务清单。 下方为上文示例对应的报告（数值与前述各图一致）：

报告解读要点

  • 首先关注 stall%。较低（如本例 8%）表明算力受限、调度良好，进一步加速须从算子实现入手； 较高则须进一步区分为 data-wait 或 core-wait。
  • 其次关注 static CPM% 与 makespan 的差距。二者接近表明依赖链即瓶颈，加核无益，应重构依赖图； 差距较大（CPM ≪ makespan）表明并行度未被充分利用，问题在于调度 / 资源。
  • 再逐行查看 family 表。关键路径上开销最高的若干算子族，即为收益最高的优化目标。
  • 务必确认 tiling check = exact。该项确保 compute 与 stall 的切分完整无遗漏。

参数速查

build_dir
位置参数：待分析目录，或任意含 l2_swimlane_records.json 的目录 / 文件。
--report
报告文件名，写在 build_dir 下（默认 critical_path_report.md）。
--top
kernel-family 表格行数（默认 25）。
--tol
判定「先于…完成」的 tick 容差（默认 2），用于吸收 tick 级并列。

额外把整份 Markdown 报告回显到 stdout。注意：每 rank 一行的摘要无论是否加此参数都会打印。

名词表

makespan
本次运行的墙钟总跨度 = max(end) − min(start)。全文百分比的分母。
static CPM
仅考虑数据依赖、假设无限核时的最长加权路径——依赖受限的延迟下界。
observed
从最后完成的任务反向回溯得到的实际归因链；含数据等待与资源串行化，其切分精确覆盖 makespan。
hb_pred
happens-before 前驱：时间前向的数据依赖边（生产者→消费者）。
core_prev
同核资源前驱：某任务落核前，该核被占用的最晚结束者。
data-wait / core-wait / front-gap
三类停顿：等待上游数据 / 等待计算核空闲 / 首个任务前的启动派发延迟。
tick → µs
设备时钟周期换算：ticks / clock_freq_hz × 1e6（a2a3 为 50 MHz，a5 为 1 GHz）。
rank
一个含三件套（records + deps + name_map）的目录，对应一个 device；工具自动递归发现全部 rank。
