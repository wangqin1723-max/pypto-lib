# 性能看护（perf-tracking）原理

> 归档日期：2026-09-15。来源：`pypto-lib/local_archive/20260817-main-cleanup/PERF_TRACKING.md`。
> 原文的实现、测量与计划保留其历史语境；阅读说明见[学习资料索引](../README.md)。

本仓库（simpler）的运行时性能是**逐 PR 连续看护**的：每落地一个 PR，就自动
把它重新编译、在 NPU 上跑基准、解析指标、和上一个 PR 对比，标出回归，最后推到
飞书。任何人都能一眼看到"是谁的 PR 让哪个 example 的哪项指标变慢了"。

驱动它的工具 `perf-tracker` 独立于本仓库存在（不在 simpler 里），但它看护的对象
就是本仓库 `tools/` 下的 `benchmark_rounds.sh`。本文说明其原理，便于其它仓库照此
搭建自己的性能看护。

---

## 1. 核心思想：把"性能"变成可追溯到每个 PR 的时间序列

传统 CI 只在单个 PR 上跑一次基准，无法回答"性能是从哪个 PR 开始退化的"。
perf-tracker 换一个视角——**以 PR 为最小单位，重建整条历史**：

```
PR#N ── checkout ── 重编译 ── 跑基准 ── 解析指标 ──┐
PR#N-1 ─ checkout ── 重编译 ── 跑基准 ── 解析指标 ──┤→ 按时间排序 → 逐 PR 算 Δ → 标回归 → 推飞书
PR#N-2 ─ ...                                        ┘
```

这套做法能成立，依赖一个关键前提：

> **PR 是 squash-merge 的**，所以 `main` 上的每一个 commit 恰好等于一个 PR 的
> 最终状态。于是"遍历 PR"退化成对 `main` 的一次 `git log`，`--recent N` 就是
> "最近 N 个 PR"，`--since '36 hours ago'` 就是"最近 36 小时落地的 PR"。

若要把这套看护搬到别的仓库，第一件事就是保证"一个 commit = 一个 PR 的可
checkout 快照"（squash-merge，或改造 PR 选取逻辑）。

---

## 2. 四段式流水线

```
 拉/更新仓库        逐 PR 重建+跑分          后处理算 Δ+标回归        推飞书
┌───────────┐   ┌──────────────────┐   ┌──────────────────┐   ┌───────────────────────┐
│  run.sh   │──▶│ perf_history.py  │──▶│ perf_finalize.py │──▶│ feishu_perf_report.py │
│（编排/网络）│   │（worktree/构建/跑分）│   │（解析/排序/Δ/告警）  │   │（原生表格/按月分文档）  │
└───────────┘   └──────────────────┘   └──────────────────┘   └───────────────────────┘
                        ▲
                        │ 并行分片（本机 NPU 锁）
                 perf_history_parallel.sh
```

### 2.1 `perf_history.py` —— 逐 PR 重建并跑分（可移植内核）

对每个 commit（旧→新）：

1. **隔离 checkout**：`git worktree add --detach <dir> <sha>`，各 commit 互不
   污染，且并行安全（`git worktree` 加/删用 `flock` 串行化）。
2. **重建 C++ 运行时**：为该 worktree 建一个
   `python -m venv --system-site-packages .venv`（从当前激活环境继承
   `scikit-build-core`/`nanobind`/`cmake` 等构建依赖），再
   `pip install --no-build-isolation -e .` 重新编译。
   - PTO-ISA 复用：从该 commit 的 `.github/workflows/ci.yml` 里解析出
     `PTO_ISA_COMMIT`，并把 `PTO_ISA_ROOT` 指向已克隆的 `build/pto-isa`，避免
     每个 worktree 都重新 clone pto-isa（在本机网络下很脆）。
3. **跑基准**：在 worktree 里执行 `tools/benchmark_rounds.sh -n <rounds>
   -r <runtime> -p <platform> -d <device>`。
4. **原样抓取 summary**：从输出里截取 `Performance Summary` 到 `Benchmark
   complete` 之间的整块文本，**逐字保存**（`extract_summary_block`）。这一步
   刻意不解析——保存原始表格，无论旧 commit 当年打印的是什么列都能存下来，解析
   留到后处理阶段做，从而对基准格式的历史变化免疫。

关键设计：**这个内核完全不知道 `task-submit` 的存在**，因此可移植——在任何能
裸跑 NPU 的机器上直接
`python perf_history.py --repo PATH -d 0 -n 5` 即可用。

崩溃安全：每跑完一个 commit 就立刻把结果 `flock` 追加进
`perf_history.jsonl`/`.md`（一次一条、加锁、并行安全），中途崩溃已完成的
commit 不丢。原始 md/jsonl **只追加、永不重写**。

### 2.2 `perf_history_parallel.sh` —— 分片到多张 NPU（本机特有）

把待测 commit 列表按 `-m` 分成 M 份，每份用 `task-submit --device N` 锁一张卡
并行跑（本机约定：普通用户用 NPU 必须经 `task-submit`）。它内建**坏卡自动切换**：

- 用显式 `--device N` 选卡（不用 `--device auto`，因为 `task-submit` 的自动
  健康视图最长 12h 才刷新，可能把刚 wedge 的卡又发回来）；优先选空闲卡少排队。
- 一张共享 NPU 可能中途 wedge（op-timeout / kernel 卡死直到复位），导致该分片
  wedge 之后的 commit **级联失败**。每轮结束后，把"尾部没跑完"（级联失败的
  特征）的卡丢进内存里的 bad set，未完成的 commit 换一张新卡重跑，最多
  `PERF_MAX_ROUNDS` 轮。
- 一个 commit 在 `PERF_MAX_ATTEMPT` 张不同卡上都失败，才认定是它自己坏
  （不是卡的问题），保留其 `rc=1` 记录。
- bad set **只存在于单次运行、从不持久化**：每天的 run 从干净状态开始，恢复了
  的卡下次自动重试，无需清理陈旧黑名单。

重试会为同一 commit 追加新的一行；后处理阶段会把一个 sha 的多行折叠成一条，
优先取成功的那次测量。

### 2.3 `perf_finalize.py` —— 解析、排序、算 Δ、标回归（只读原始数据）

只读 `perf_history.jsonl` 及分片日志，把加工结果写到 `*_processed.*`，**绝不
改动原始数据**。做四件事：

1. **回填 NPU 编号**：从分片日志 + `task-submit` 记录还原每个 commit 实际跑在
   哪张卡上（权威来源）。
2. **解析 summary**：把逐字保存的表格块解析成
   `{example: {metric: value}}`。解析按表头里 `(us)` 列的**位置**对齐，所以
   基准新增一列（如 `Effective (us)`）或多一个非数字前导列（如 `Mode`）都不会
   错位；只保留跟踪的 `METRICS = [Host, Device, Total, Sched, Orch]`。
3. **排序**：按 commit 时间**新→旧**。
4. **算 Δ 并标回归**：每个指标显示相对**上一个（更老）commit** 的百分比变化，
   如 `2704.0 (-3.0%)`。跨过阈值打标记：`🔺 变慢 ≥5%` / `🔻 变快 ≥5%`；
   commit 级告警：设备侧指标（`Device/Total/Sched/Orch`，`Host` 太噪不计）
   回归 `≥10%` 就在标题和顶部"重点关注"里 `⚠️` 标出（并有小基线下限过滤掉
   ~6µs 的 Orch 之类噪声项）。

两个防对不上的设计（跨天增量的关键）：

- **跨窗口基线**：每天的 run 只截取 ~36h 窗口，窗口里最老的 commit 没有窗口内
  的前驱，Δ 会空。finalize 会读回上一次 run 的 `_processed.jsonl`，捞出其中
  仍相关的最新一条作为基线锚点，让每天窗口的第一个 commit 也有 Δ。
- **冻结已发布指标**：36h 窗口有重叠，会把已发过的 commit 再测一遍。若用新测量
  值当基线，新 commit 的 Δ 会跟飞书文档里显示的旧值对不上。所以对已发布的
  sha，finalize **复用已发布的指标**（飞书按 sha 去重、已发的行不更新），保证
  "文档里显示的值"和"用来算下一个 commit Δ 的基线"永远一致。

### 2.4 `feishu_perf_report.py` —— 推飞书（原生表格 + 按月分文档）

从 `_processed.jsonl` 构造**飞书原生表格**（不是代码块），逐 commit 生成
"标题 + 元信息 + 指标表"，按日期分组。为控制单页体积，**按月拆成多个文档 + 一个
索引文档**；索引里每月一条链接。核心是 `--publish` + `--state`：

- state 文件记录 `month → doc_id` 和已推的 sha 集合；每次都传入完整有序集合
  （保证 Δ 正确），但只写 `state["pushed"]` 里没有的 commit，所以对不断增长的
  归档**幂等、绝不重复**。
- daily：新 commit **prepend** 到当月文档顶部（新在上）。
- backfill（`--append`）：逐渐更老的 commit **append** 到底部，维持新在上。
- `--rebuild`：清空所有月文档、重置 pushed 集，用完整有序归档重写一遍（保留
  索引 URL 不变）。
- run.sh 会推**两份独立文档**：主报告（带 Δ 和告警）＋ `--no-delta` 的纯实测值
  文档（只有原始数字），各用各的 state 文件。

## 3. `run.sh` —— 编排与工程韧性

`run.sh` 是入口，把上面四段串起来，并处理本机的现实约束：

- **默认窗口 >24h（36h）是刻意的**：本机 GitHub egress 不稳，某天 run 失败时，
  第二天有重叠的窗口会自动补测；飞书按 sha 去重，重叠部分不会重复发。
- **GitHub egress 探测**：clone/fetch 前先探通路——**先 SSH，再本机 http 代理
  （4780/4781），最后直连 https**（`pypto-setup` 约定），并对瞬时 SSL 超时
  重试。不锁死端口，因为共享机上可用通路会漂移。fetch 彻底失败时保留旧 clone
  继续跑（发软告警），让 36h 窗口下次补回。
- **失败即钉钉/飞书告警**：任何非零退出都发一张飞书失败卡片，注明是哪个阶段
  （egress/benchmark/finalize/publish）挂的。
- **时间不可信**：本机系统时钟被人改过，所以报告/通知里的时间戳走**网络时间**
  （`nettime.py` 读 HTTP `Date:` 头，走同样的代理/直连），网络不可达才回退本机
  时钟并在 stderr 标注。cron 用 `CRON_TZ=Asia/Shanghai` 只钉时区（北京 22:00
  触发），真实触发时刻仍依赖系统时钟由 NTP 校准。

## 4. 数据产物

| 文件 | 内容 |
| ---- | ---- |
| `perf_history.md` / `.jsonl` | **原始**、只追加、崩溃安全（一次一条 + flock） |
| `perf_history_processed.md` / `.jsonl` | NPU 标注、新→旧排序、带 ΔDevice/ΔOrch 及回归告警。已发布 commit 冻结 |
| `feishu_state*.json` | 飞书 `month→doc_id` + 已推 sha 集，保证幂等 |
| `simpler/` | 被看护的托管 clone（worktree 建在 `perf_worktrees/`） |

---

## 5. 照此看护别的仓库要替换的三处

流水线骨架（Δ 计算、去重、崩溃安全、按月推送、坏卡切换）可整体复用，仓库相关的
只有三处：

| 环节 | simpler 现状 | 换成你的 |
| ---- | ---- | ---- |
| PR 选取 | squash-merge → `git log` | 保证"一个 commit = 一个 PR 快照" |
| 构建 | `venv --system-site-packages` + `pip install -e .` + 复用 PTO-ISA | 你的构建命令与依赖 |
| 跑分 + 解析 | `benchmark_rounds.sh` + 抓 `Performance Summary` + 位置对齐解析 | 你的基准脚本 + 指标解析 |
