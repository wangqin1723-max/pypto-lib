SIMPLER · PR #1314

让“值还没算出来”
不再卡住编排线程

Predicated Dispatch 把“这个任务到底要不要发射”的判断推迟到任务真正 ready 的时刻。上层仍可静态铺开任务图，同时跳过运行时为空的工作，并保持 orch pipeline 向前流动。

一句话：提交条件，不在 orch 里等待条件。
三阶段流程 上层如何表达 更多适用形态 收益与边界 采用检查
From MoE to the common pattern

生产者 tensor 决定消费者是否下发：看三个阶段的流水变化

MoE 只是这个问题的来源：上游路由/dispatch 产生 recv_expert_count，记录每个 local expert 接收到多少 token row。这个 tensor 的值决定后续 expert stage 是否有实际工作。抽象出来就是：一个 producer 的输出 tensor 决定一个 consumer task 是否需要下发。

要优化的不是 kernel 内的一行 if。真正的目标是让“空 consumer”尽早停在调度侧：既不要让 orch 为了读条件而阻塞，也不要把必然空的任务继续下发到 AICore。

阶段一：PR #738 之前，orch 用 get_tensor_data 决定是否提交消费者

这条路能跳过空 consumer，但判断发生在 orch 线程。get_tensor_data 必须拿到 producer 已完成的 tensor 值；如果值还没 ready，orch 就等在这里。producer 完成、count 可读之后，orch 才能判断是否提交 consumer；consumer 一旦提交，后续仍按“scheduler 下发 → AICore 执行”的正常链路推进。

阶段二：PR #738 之后，上层不再读 count，消费者全部提交

PR #738 的优化方向是把判断下沉到 consumer kernel 内：每个 expert stage 统一提交一次，kernel 里读取 recv_expert_count，算出 n_tiles，再执行 for t in range(n_tiles)。这样 orch 不再被 get_tensor_data 卡住，能更快把任务图铺出去；但副作用是空 consumer 也会进入 scheduler 和 AICore。

阶段三：加上 PR #1314，orch 提交条件，scheduler 在 ready 点判断

Predicated Dispatch 保留 PR #738 的流水优势：orch 不同步读取 count，只提交“consumer + predicate 地址”。等 count producer 依赖完成、consumer 到达 ready 点时，scheduler 读取这个 tensor 元素并比较；真值才下发到 AICore，假值直接退休。这样同时得到两件事：orch 不被 get_tensor_data 阻塞，空任务也不再下发。

性能效果怎么理解

流水恢复 + 空任务不下发

阶段二已经去掉了 orch 同步读 count 的阻塞，但留下空任务下发；阶段三在不牺牲 orch 流水的前提下，把 false consumer 截在 scheduler ready 点，进一步省掉冗余下发和空 kernel 启停。

How upper layers express it

上层表达的是“发射条件”，不是提前读取的布尔值

条件由一个 GM tensor 元素、比较操作和常量目标组成。关键是把 predicate operand 的 producer 纳入被条件化任务的依赖，保证 task ready 时该值已经可读。

最重要的正确性契约：predicate operand 的 producer 必须是 predicated task 的依赖。否则“task ready”不能证明条件值已更新，判断可能读到旧值。运行时不会替上层推断这条依赖。

Pattern catalog

它适合“图可静态展开、工作是否为空由设备侧结果决定”的任务

例 1 · MoE 空 expert

expert_count[i] > 0

固定提交每个 local expert 的 stage；无 token 的 expert 不发射。条件对整个 SPMD task 一致：通过则所有 block 正常发射，失败则一个 block 都不发射。

例 2 · 稀疏分桶

bucket_size[i] != 0

上游统计各 bucket 的元素数，下游为每个 bucket 静态准备处理任务。空 bucket 直接退休；非空 bucket 保持原计算路径。

例 3 · 可选后处理

valid_count > threshold

上游产生有效元素计数，只有达到阈值才运行后处理。前提是跳过后不会让消费者读取本应由该任务生成的新输出。

不要把它当成通用 if。它控制的是“整个 task 是否 dispatch”，不是 kernel 内每个 block、每个 tile 或每个元素的分支。需要细粒度条件时，仍应在 kernel 内处理。

收益更容易成立

  • 空任务比例可观，且空任务下发 / 空 kernel 启停成本不可忽略；
  • 旧路径需要在 orch 中用 get_tensor_data 读取 producer 输出；
  • orch 被 get_tensor_data 卡住时，本来还有其他独立任务可继续提交；
  • 保持静态任务图比在 orch 动态决定任务数量更合适。

收益可能很小，甚至不合适

  • 条件在 submit 前已是现成的 host / orch 标量，无需等待；
  • 几乎所有 predicate 都为真，只额外增加调度侧 GM 读取；
  • 跳过任务后，后继仍会读取该任务本应写出的新结果；
  • 需要按 block 或 tile 分别决定执行，而不是 task-level 统一条件。
如何理解端到端收益：大致来自两部分：一是 orch 不再为 get_tensor_data 等 producer ready；二是 false task 不再下发到 AICore，也没有空 kernel 启停。需要扣掉的成本是 scheduler 在 ready 点读取一个 GM 元素并比较，以及仍然存在的任务创建、提交、payload 和依赖记账。具体数值取决于 false 比例、producer 延迟、可重叠工作和 kernel 粒度，需要在目标 workload 上测量。
Adoption checklist

准备把一个上层算子改成 predicated dispatch 前

语义检查

  1. 条件是否来自一个已生产的 GM tensor 元素？
  2. 是否已把该 producer 显式放进 task 依赖？
  3. predicate false 时，任务不写输出是否仍然正确？
  4. 后继解锁后是否不会读取未生成或过期的数据？
  5. 条件是否对整个 SPMD task 的所有 blocks 一致？

性能检查

  1. 先统计 false / 空任务比例，而不是只凭直觉；
  2. 确认旧路径确实在 orch 的 get_tensor_data 等待上形成气泡；
  3. 分别观察 orch/scheduler 时间、dispatch 数和端到端时延；
  4. 同时覆盖 predicate true 与 false 两条正确性路径；
  5. 对 SPMD 验证 false 时没有 block 被发射。
当前能力范围（PR #1314）：落在 a2a3 与 a5 的 tensormap_and_ringbuffer runtime；支持 task-level EQ / NE / GT / LT / GE / LE 比较。当前实现按有符号整数读取 1/2/4/8 字节 operand。前端 pl.spmd(predicate=...) 是独立 follow-up，不应把本文示意语法当作已经发布的 pypto API。
