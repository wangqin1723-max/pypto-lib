# 2026年8月26日 MoE 统计驱动专家分配任务

> 归档日期：2026-09-15。来源：`pypto-lib/local_archive/2026年8月26日-MoE统计驱动专家分配任务.md`。
> 原文的实现、测量与计划保留其历史语境；阅读说明见[学习资料索引](../README.md)。

## 1. 要解决的问题

原来的流程：

- 当前维护的 EPLB 基线分支为 `upstream/perf/dsv4-eplb-decode-logits-and-mtp-core`，原始基线提交为 `4c633d4`。新平行分支把这 7 个 EPLB commit rebase 到 `upstream/main@7ac8e24`，得到等价基线 tip `63b5d43`，原 EPLB 分支和入口未修改。
- 该分支使用 EP8、每 rank 16 个专家、共 128 个物理专家的合成负载。
- 384 条 route 被均匀分配到 128 个专家，每个专家固定收到 3 条 route；各层复用同一份 round-robin `tid2eid`，MoE 调用被固定到 hash layer 0。
- dispatch 直接把 expert ID 当作物理 ID，按 `dst_rank = eid // N_LOCAL`、`local_slot = eid % N_LOCAL` 定位专家，没有独立的逻辑专家到物理 slot 映射。
- 该流程适合做理想均衡负载下的性能基线，但不能表达 `moe-stats.jsonl` 中逐层不同的专家热度。

具体问题：

- `moe-stats.jsonl` 对应 EP8、每 rank 32 个专家、共 256 个专家，与现有 EPLB 分支的 128 专家拓扑不一致，不能只替换 `tid2eid`。
- 文件包含 215 次 dispatch、44 层，其中主模型为 layer 0～42，MTP 为 layer 43；每层提供 256 个 `expert_token_counts`。
- phase 包括 4 条 `prefill`、64 条 `mtp_prefill` 和 147 条 `decode_mtp`。其中 141 条完整 `decode_mtp` 的每层 route 数为 384，与当前 decode benchmark 的 route 规模一致。
- stats 只提供每次 dispatch、每层、每个专家的 route 计数，没有逐 token 路由、source-rank 到 expert 的流量矩阵、请求 ID、当前物理映射和专家执行时间。因此可以优化目标 rank 的专家负载，但不能精确重放原始 AllToAll 通信，也不能直接推导端到端加速比。
- “不再每层 EPLB”的准确含义待确定。本文默认解释为：不在运行时逐层执行 EPLB，而是离线生成逐层固定 placement，部署期间直接使用静态结果。逐层静态表不等于运行时逐层 EPLB。
- 如果需求是 44 层共用同一张 placement，是否必须如此待确定。当前数据初步显示各层热点差异很大，共用一张表难以平衡单层负载，因此不建议作为默认实现。

本次目标：

- 已新建平行分支 `perf/dsv4-stats-placement-decode-logits-and-mtp-core`，保留现有 EPLB 分支和入口作为基线。
- 第一阶段固定为 EP8 × 32、256 个逻辑专家、每个专家一个物理副本；是否支持专家复制待确定。
- 根据 `moe-stats.jsonl` 离线生成 44 份固定 placement，运行时不再计算 EPLB。
- placement 必须可复现、可校验，并与 stats 来源、phase 选择、算法版本和权重转换结果绑定。
- 在相同 256 专家、相同权重、相同输入和相同路由负载下，对比 contiguous placement 与 stats placement 的正确性和真实性能。
- 第一版已确定只覆盖 decode/MTP 的 stats-shaped hash-route replay benchmark；prefill、真实 checkpoint 权重加载和生产部署仍待确定。

分支创建：已完成，并使用独立 worktree 隔离开发。

代码实现：已完成第一版方案 A。新增离线生成器、版本化 manifest、host 侧 9 类 MoE tensor 同步置换、43 层 full decode 入口、layer 43 MTP 入口，以及相同 EP8×32 stats workload 下的 contiguous/stats 对照 runner；dispatch kernel ABI 和运行时关键路径未增加 mapping lookup。

PR：待确定。

## 2. 数据流

输入：

- 文件：`moe-stats.jsonl`。
- 记录数：215。
- 拓扑：`ranks=8`、`local_experts=32`、总专家数 256。
- shape：每条记录包含 44 层，每层 `expert_token_counts` 的 shape 为 `[256]`。
- layout：`expert_token_counts[i]` 暂按逻辑 expert `i` 理解；它是否已经经过某种物理重映射待确定，实施前必须由数据生产方确认。
- 所在 rank：stats 是 host 侧离线输入，不属于任何 device rank。
- 优化 phase：第一版固定使用 `phase=decode_mtp` 且 `routed_tokens=384` 的 141 条完整 dispatch，避免将 prefill、MTP prefill 和 decode 按采样条数直接混合。
- phase 权重、dispatch 时间范围和 trace 代表性：待确定。

处理过程：

1. 逐行解析 JSONL，校验 schema、dispatch 顺序、44 层、每层 256 个计数，以及 `sum(expert_token_counts) == routed_tokens`。
2. 按确定后的 phase、dispatch 范围和权重聚合每层每个逻辑专家的 route 数。
3. 对每层独立求解 256 个逻辑专家到 8 × 32 个物理 slot 的双射，约束每个 rank 恰好放置 32 个专家，目标是降低最大 rank 的预测负载。
4. 第一版 placement 算法建议使用带确定性 tie-break 的 capacity-constrained LPT，再做局部 swap；是否需要 ILP、p95-aware 或多 phase 最坏值目标待确定。
5. 生成版本化 manifest，记录 source SHA256、schema、算法版本、phase 过滤条件、拓扑、逐层映射和预测负载。
6. 按方案 A 在 host 侧展开为物理布局，或按方案 B 在 dispatch 前执行逻辑 ID 到物理 ID 的查表。
7. 如果 benchmark 仍使用 hash fixture，需要根据专家直方图合成合法的 `[tokens, TOPK]` 路由。stats 不包含 token 级共现和 source-rank 信息，因此只能保证专家计数一致，具体重建规则待确定，不能称为精确 replay。
8. 如果使用真实 gate 路由，则需要加载真实输入和权重；数据来源及 golden 方式待确定。

输出：

- 主映射 shape：`logical_to_physical[44][256]`。
- 建议同时输出的逆映射 shape：`rank_to_logical[44][8][32]`。
- layout：`physical_eid = rank * 32 + local_slot`，每层映射必须是 `0..255` 的双射。
- 所在 rank：manifest 在 host 侧生成和校验；方案 A 在加载权重时展开，方案 B 还需要把映射复制到各 device rank。
- provenance：stats SHA256、phase/dispatch 过滤条件、算法及版本、拓扑、生成时间。
- manifest 使用版本化 JSON，存放于 `models/deepseek_v4_flash_mtp/stats_placement_decode_manifest.json`；运行时只加载 manifest，不直接解析约 5.8 MB 的原始 JSONL。原始 JSONL 是否提交仓库仍待确定。

## 3. 方案选择

候选方案 A：离线逐层固定 placement，并在 host 侧重排 router 数据和专家权重。

处理方式：

- hash-routing 层把 `tid2eid` 中的逻辑 expert ID 转成物理 expert ID。
- score-routing 层按同一 placement 重排 `gate_w` 和 `gate_bias`，使 top-k 直接输出物理 expert ID。
- routed expert weights 和 scales 按逐层 placement 放入对应 rank/local slot。
- dispatch 保持现有 `eid // N_LOCAL` 和 `eid % N_LOCAL` 逻辑，不增加运行时查表。
- placement 是部署前生成的 44 份静态表，不在每层执行时重新计算。

优点：

- kernel ABI 和 dispatch 关键路径基本不变，运行时没有额外 mapping lookup。
- 现有 dispatch、通信窗口和大部分 golden 逻辑可以复用，第一阶段改动范围较小。
- manifest、权重和路由表可以通过 fingerprint 强绑定，结果容易复现。
- 最适合先验证 stats placement 是否能在真实 EP8 设备上带来收益。

缺点：

- placement 变化后需要重新转换或加载 gate 和 routed expert 权重。
- 静态布局不能自动适应 workload 漂移，也不能在 prefill/decode 之间无成本切换。
- 完全相同 score 的专家可能因 gate 行重排改变稳定排序的 tie 顺序；是否接受待确定。
- 若先构造完整 stacked weights 再重排，可能增加接近一份权重的 host 内存，应尽量在 loader 中直接 gather 到目标布局。

候选方案 B：router 保持逻辑 expert ID，在运行时查表得到物理 expert ID。

处理方式：

- hash `tid2eid`、`gate_w` 和 `gate_bias` 保持逻辑专家顺序。
- 新增 `logical_to_physical[layer][logical_eid]` mapping tensor，在 dispatch 前把逻辑 ID 转成物理 rank/local slot。
- routed expert weights 仍必须按所选 placement 放到物理 slot，mapping 与权重布局必须使用同一版本。
- 第一阶段只考虑模型加载时选择一份静态 mapping。运行中周期性重新分配还需要专家权重迁移、双缓冲、全 rank 同步和回滚，是否需要另行待确定。

优点：

- router 的逻辑专家顺序不变，能够保留原有 top-k tie 语义。
- placement 与 router 参数解耦，同一模型可以在加载时选择不同 profile。
- 接口更接近后续 phase-specific placement、专家复制或在线调整的演进方向。

缺点：

- 需要修改 `moe`、dispatch、golden、tensor specs 和各模型入口，kernel ABI 影响更广。
- 每条 route 增加查表和依赖，可能侵蚀负载均衡收益，具体开销待实测。
- 所有 rank 的 mapping 与权重版本必须一致，否则会把 token 发给错误专家并产生静默错误。
- 仅更新 mapping 不能移动专家，真正在线调整还需要权重迁移、同步、安全切换点和额外内存，第一阶段不具备这些能力。

我的选择：

我倾向于先实现方案 A，因为当前需求首先需要验证“历史 stats 生成的固定 placement”是否有效，而方案 A 对 kernel 关键路径和现有 EPLB overlay 的侵入最小。两种方案可以共用同一种 manifest schema；只有在实测证明 workload 漂移或 phase 冲突足以覆盖查表和迁移成本后，再考虑方案 B。

|---|---|---|---|
| `tools/generate_dsv4_moe_placement.py` | JSONL `[dispatch][44][256]` → manifest `[44][256]` | 严格校验 stats、过滤 phase、聚合负载、生成确定性 placement 和 provenance | 把运行时 EPLB 变成可复现的离线步骤 |
| `models/deepseek_v4_flash_mtp/stats_placement_fixture.py` | manifest → 双射、容量、版本和 hash 校验结果；logical route/weights → physical route/weights | 校验 manifest、生成 stats-shaped fixture，并集中实现 host 侧 permutation | 防止错误布局或旧缓存被静默使用，并保证 9 类 MoE tensor 使用同一映射 |
| `models/deepseek_v4_flash_mtp/stats_placement_decode_logits.py` | layer 0～42 placement + decode inputs → logits | 复用原 EPLB kernel，逐层切换静态布局并重放逐层统计负载 | 新入口与原 EPLB 入口隔离，避免改变基线行为 |
| `models/deepseek_v4_flash_mtp/stats_placement_mtp_core.py` | layer 43 placement + MTP inputs → MTP outputs | 为 MTP 使用独立 placement | MTP 热点分布和主模型不同，不能复用 layer 0 |

| `models/deepseek_v4_flash_mtp/moe.py` | routed IDs → rank/local slot | 方案 A 保持不变；方案 B 增加 logical-to-physical lookup，并同步 golden | dispatch 当前直接把 expert ID 当物理 ID |
| `models/deepseek_v4_pro/utils/weights_flash.py`（若接真实权重） | checkpoint + placement → 各 rank 物理专家权重 | 在权重加载时直接按 placement gather，并绑定转换缓存 fingerprint | 避免逻辑 ID、物理 slot 和转换缓存不一致 |
| `tests/contract/test_dsv4_*stats*` | identity/permutation/异常 manifest → pass/fail | 校验映射、host transform、route 合成、接口和 overlay contract | full decode overlay 当前没有完整数值 golden，必须补映射一致性证据 |

## 5. 同步与生命周期

- 谁生产数据：`moe-stats.jsonl` 由外部采集流程生产，采集工具、模型版本、checkpoint、流量来源和采样规则待确定；placement manifest 由离线生成器生产。
- 谁消费数据：host 侧 fixture 或权重 loader 消费 manifest；方案 A 的 kernel 只消费已经重排的物理 ID/权重，方案 B 的 kernel 还消费 mapping tensor。
- 如何通知 ready：方案 A 在加载前完成 manifest 与权重 fingerprint 校验，不增加 device 侧 ready 通知；方案 B 需要保证 mapping 在 dispatch 前已复制到所有 rank，具体 barrier/event 机制待确定。
- buffer 什么时候可以复用：原始 stats 在生成 manifest 后不进入运行时；manifest 和重排后的权重在整个模型实例生命周期内保持有效。方案 B 的 mapping buffer 在所有引用该版本的 in-flight dispatch 完成前不可复用或覆盖。
- 出错可能导致什么：路由 ID、gate 行、专家权重、scales 或 mapping 任一侧版本不一致，会把 token 送到错误专家，可能产生数值正常但语义错误的静默结果；不同 rank 使用不同 mapping 还可能导致错误通信和越界。
- 多版本切换：第一阶段不做运行中 mapping 切换。若后续需要，权重迁移、双缓冲、safe point、全 rank 原子发布和回滚协议全部待确定，并应单独立项。

## 6. 正确性与性能验证

正确性：

- 测试方式：
  - 校验 215 条 stats 均可解析，每条 44 层，每层 256 个计数，且计数和等于 `routed_tokens`。
  - 校验每层 placement 是 `0..255` 的双射，每个 rank 恰有 32 个专家，相同输入重复生成结果一致。
  - 分别验证 `tid2eid`、`gate_w/gate_bias`、routed weights/scales 的 permutation 使用同一映射。
  - 做 metamorphic 测试：contiguous logical layout 与重排后的 physical layout 在相同逻辑输入下输出等价。
  - 覆盖 hash layer、score layer、主模型 layer 42、MTP layer 43、identity mapping 和随机 permutation。
  - 先验证 `golden_moe()` 和 MTP 组件，再补 full logits 或 contiguous-vs-placed 对照；full decode golden 的具体入口待确定。
  - mapping、权重或 cache fingerprint 不一致时必须显式失败，不能回退为未校验运行。
- 精度阈值：待确定，应复用对应模型/组件现有 golden 阈值；若只比较纯 permutation，CPU 逻辑结果应精确一致，浮点 kernel 结果按现有 dtype 容差比较。
- 边界场景：零热度专家、单专家热点、相同负载 tie、相同 gate score tie、tail dispatch（96/192/288 routes）、错误拓扑、缺层、重复 expert、过期 manifest、MTP 独立布局。

性能：

- 对比基线：同一 EP8×32、256 专家、同权重、同输入和同 route workload 下的 contiguous placement。旧 EP8×16 的均匀 EPLB 只能作为理想均衡控制组，不能作为收益基线。
- 观察指标：逐 dispatch 最大 rank route 数、最大 rank/平均 rank 负载比、各 rank kernel 时延、AllToAll 时延、MoE 端到端时延、整模型时延和吞吐。
- 离线试算：对 141 条完整 `decode_mtp` 记录做逐层静态 placement，理想平均值为每 rank 48 routes。使用同一批数据生成并评估时，最大 rank route 数的均值约从 89.18 降到 56.73，p95 从 132 降到 64，最大值从 253 降到 70。该结果是 route-count proxy 和 in-sample 估计，不是设备性能结果。
- 泛化试算：按时间顺序以前 70 条生成、后 71 条评估时，最大 rank route 数均值约从 86.86 降到 60.80，p95 从 126 降到 71，最大值从 159 降到 113。该结果仍不包含通信和 kernel cost。
- 测试平台、warmup、rounds、统计口径和性能通过阈值：待确定。
- 离线 stats-shaped replay 结果：44 层每层 384 routes，contiguous placement 的最大 rank route 数均值为 85.93、全层最大值为 138；stats placement 分别为 49.80 和 61，44 层均未退化。这是 route-count proxy，不是设备性能结果。
- 实现验证：新 generator/route/permutation/runner contract tests 与原 EPLB 定向回归均已通过；full decode 和 MTP 新入口均通过 compile-only。真实 EP8 设备性能与端到端数值验证待确定，当前未占用设备。

## 7. 我的判断与疑问

我的判断：

- 需求可以实现，但应定义为“离线按层生成静态 placement”，而不是 44 层共用一张映射，也不是运行时每层重新做 EPLB。
- 第一版应采用方案 A、EP8×32、256 专家一一放置，不做复制，不改 dispatch 关键路径。
- 现有均匀 round-robin fixture 必须替换为 stats-shaped workload 或真实 gate workload；否则改变 placement 也看不到收益。
- MTP layer 43 应有独立 placement。
- 两种方案应共用同一 manifest 表达和 fingerprint 规则，避免后续重复设计。

目前的担忧：

- stats 只有约 54 秒数据，且疑似只覆盖少量请求，是否代表线上长期流量待确定。
- prefill、mtp_prefill 和 decode 的热点分布不同，错误的 phase 权重可能提升一种场景却损害另一种场景。
- stats 缺少 source-rank 流量，计算负载改善不一定等比例改善 AllToAll 或端到端时延。
- stats 缺少 token 级路由，合成 fixture 不能恢复原始 token 共现、route 顺序和源 rank 分布。
- router ID、物理专家权重和 manifest 只要有一侧错位，就可能出现难以察觉的静默正确性问题。
- 当前 full decode overlay 没有完整 golden，只跑通或性能变快不能证明映射正确。

尚未确认：

- 待确定：`expert_token_counts[i]` 是否是重映射前的逻辑 expert `i`。
- 待确定：目标只优化 `decode_mtp`，还是按明确权重同时优化 prefill、mtp_prefill 和 decode。
- 待确定：是否要求所有 44 层共用一张 placement；当前建议每层一张离线固定表。
- 已确定：第一版使用合成 stats-shaped hash-route replay；真实 gate 输入和真实权重另行处理。
- 待确定：是否只做单副本双射，还是需要复制热点专家。
- 已确定：生成器和版本化 manifest 放入新分支；原始 stats 是否提交仍待确定。
- 已确定：新分支以 `upstream/main@7ac8e24` 加 rebased EPLB commit stack 为基线，分支名为 `perf/dsv4-stats-placement-decode-logits-and-mtp-core`；owner、排期和 PR 仍待确定。
- 待确定：真实 checkpoint、权重转换缓存、测试设备、测试次数、精度阈值和性能验收线。
- 待确定：prefill 与 decode 是否必须共享一套常驻权重布局，还是允许 phase 边界切换。

如果重新设计，我可能会：

- 让采集端增加 source-rank × logical-expert 的流量矩阵、模型/checkpoint fingerprint、TOPK、token 数和每个专家的实测执行成本。
- 将优化目标从单纯 route 数升级为预计 tile 工作量、专家 kernel cost、AllToAll 流量和跨 dispatch p95 的组合目标。
- 如果长期 workload 漂移明显，再引入多 profile 或方案 B；运行中在线迁移和专家复制另行设计，不放入第一版。
