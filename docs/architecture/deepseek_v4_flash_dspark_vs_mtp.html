01 · direct answer

先更正：运行方式不同，但预测层并不是完全分开的

MTP-1 与 DSpark 是两种不同的推测解码运行契约；DeepSeek-V4 DSpark 又复用了 MTP 命名的预测层作为自己的草稿骨干。因此不能说“完全无关”，也不能把它们串成“MTP 先逐 token 生成，DSpark 再验证”。

传统 MTP · 当前 MTP=1
一层预测，一轮产生一枚草稿

当前本地 MTP 路径使用一个额外预测层，生成一枚草稿，下一轮由主模型验证。它的运行形状是 [tail, draft]，不是七位置块。

10 · common confusions

四个最容易讲错的点

1. MTP 与 DSpark 到底是分开还是包含关系？
从运行方式看，它们是可替换的两种 speculative method；从 DeepSeek-V4 DSpark 的模型内部看，DSpark 又包含三层存放在 mtp.0/1/2 下的预测骨干。准确说法是“运行契约不同，但 DSpark 复用了 MTP 命名/训练出来的预测层”，不是“完全无关”。
2. 三个 Prediction Layer 是否分别生成三枚 token？
不是。三个层依次变换同一个七位置 hidden block，中间没有 LM Head 和 token 采样。第三层完成后，统一输出头一次产生七个位置的基础 logits；随后 Markov Head 才从 anchor 开始顺序采样七枚草稿。
3. DSpark 是否负责判断哪些 token 真正可接受？
不是。可选 Confidence Head / scheduler 只能裁剪“值得送去验证”的候选长度；真正比较候选并接受连续正确前缀的是下一次完整主模型前向及 rejection sampler。issue #905 当前固定形状仍是主模型验证 1 + 7 = 8 个位置。
4. 为什么这里是 43 层，不是 61 层？
当前 issue #905 与 models/deepseek_v4_flash_dspark/ 使用的是 V4-Flash：FLASH.num_hidden_layers = 43，DSpark 取第 40、41、42 层 hidden。61 层属于 V4-Pro preset，是另一模型目录和工作点。
5. TP 是不是只有 DSpark Decode 才需要？
不是。TP 解决的是一次模型计算怎样分给多张卡，普通 Decode、MTP 或 DSpark 都可能使用。当前优先 DSpark，只是因为真实部署点带来了明确的 T=512, TP=4 验证形状。
6. 独立算子精度通过，能不能直接测端到端性能？
可以测该算子的局部性能，但端到端结论需要真实高层调用、跨卡窗口与信号、分片权重加载、请求状态、草稿接受逻辑全部进入同一条执行路径。当前 DSpark 目录还没有满足这个条件。

这个结论从哪里来？

  • Issue #905 · P6明确写明 DSpark 是 block drafter、不是 serial MTP，但权重位于 checkpoint 的 mtp.* 命名空间。
  • Issue #935 · DSpark drafter contract明确规定三层骨干使用 mtp.0/1/2，第三层之后再由 Markov Head 顺序产生七枚 token。
  • vLLM Ascend · deepseek_v4_dspark.py构造三层 DSpark decoder，并把 checkpoint 的 mtp.{stage} 权重映射进 DSpark 模型。
  • vLLM Ascend · DSpark sampling loop先得到整块 base logits，再循环执行 Markov bias 与 argmax，产生七枚草稿。
  • DSpark 论文 · Figure 1 / §3主模型先给 anchor，DSpark 提议候选块，最后仍由主模型验证。
