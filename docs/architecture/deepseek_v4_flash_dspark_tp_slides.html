01 · 两个独立维度

DSpark 与 TP，解决的不是同一个问题

DSpark · Speculative Decoding
少调几次

决定一次提出、验证多少个位置

草稿器先给候选，主模型批量验证，减少主模型调用轮次。

TP · Tensor Parallel
多卡分担

决定一次模型计算怎样分到多卡

按组件选择 token 归属、权重复制、权重分片和通信边界。

结论：普通 Decode 也可以使用 TP；当前只是优先对齐 DSpark Decode 的真实部署形态。
02 · Proposal → Verify

DSpark：一次提出 7 个，主模型验证 8 个位置

草稿器 向前提出最多 7 个候选 token

06 · Communication Boundaries

三次跨卡操作，各自解决一种布局变化

01 · AllGather-like

Hidden 收集

128 行 → 512 行

只复制，不求和。让每张卡获得完整 KV 输入。

02 · AllToAll-like

Attention 结果互换

本卡 token → 本卡输出组

只重排，不求和。将归属轴从 token 换成 head 输出组。

03 · ReduceScatter-like

输出部分和合并

512 行部分和 → 128 行结果

FP32 求和后按 token 返回，再转换为 BF16。

通用原则：通信发生在数据布局改变的地方，而不是因为某个算子名字里有 TP。

11 · Takeaways

记住三句话

1

DSpark 决定一次验证多少个位置；TP 决定这次主模型计算怎样分到多卡。

2

TP 的工程核心是组件间的数据布局和通信边界，不是把所有维度简单除以四。

3

四卡 Attention 基础和独立草稿器算子已经存在；端到端接入、对账与性能仍待完成。
